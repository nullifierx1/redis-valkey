# Правила работы над проектом

## Архитектура и структура

- Соблюдать SOLID и GRASP. У компонента должна быть конкретная ответственность и проверяемый контракт.
- OCP — критерий расширения: новые команды, семейства и грамматики подключаются через модули и регистрацию без изменения ядра диспетчера и парсера.
- Выделять связанные операции и инварианты в классы. Общие механизмы скрывать за публичным контрактом; namespace использовать для группировки имён, а не вместо сущности с ответственностью.
- Не вводить состояние, наследование или интерфейсы без конкретной задачи. Контракты семейств должны задавать полезное поведение, а не служить пустыми метками.
- Сохранять структуру проекта: тесты размещать по контексту в существующих тестовых файлах; новые файлы создавать для самостоятельных компонентов.
- Переиспользуемые concepts размещать в `include/concepts/`, по одному смысловому контракту на файл. Они не должны зависеть от конкретных команд.
- Менять одну архитектурную границу за этап. Задачи и критерии готовности находятся в `todo.md`.

## Типы и контракты API

- Использовать возможности C++20, стандартные алгоритмы и готовые traits из `<type_traits>`. Concepts задают ограничения API и могут объединять стандартные traits; не перечислять вручную все допустимые типы, если контракт выражается через их свойства.
- Проверять ограничения шаблонов на допустимых и недопустимых типах. Не полагаться только на доступность сигнатуры, если ошибка может возникнуть при инстанцировании тела функции.
- Использовать `[[nodiscard]]` для результатов, игнорирование которых теряет значение, статус или ошибку: парсинг, валидация, поиск, операции с существенным исходом.
- Возвращать VO для значений с предметными инвариантами; `bool` — для предикатов и простого двоичного исхода; `Result`/`ResultType` — когда нужны значение или причина отказа.
- `void` допустим, когда вызывающей стороне не нужен результат. Не заменять его формальным `true`, не несущим информации.
- Сохранять полезную информацию результата операции. Например, использовать итератор и флаг вставки, возвращаемые `try_emplace`/`insert`, если они нужны вызывающему коду; не делать повторный поиск для получения уже доступных данных.
- Для собственных операций с несколькими значимыми результатами выбирать понятный тип результата с именованными полями; не добавлять поля без сценария использования.

## Читаемость и комментарии

- Имена типов и методов должны объяснять назначение кода. Не комментировать очевидное и не пересказывать инструкции построчно.
- Комментарии нужны для неочевидных ограничений, причин решения и внешних требований. Документировать нетривиальные публичные контракты, не дублируя их сигнатуры.
- Не выполнять массовые несвязанные изменения при работе над небольшим этапом.

## Тесты и обязательный hook

- Hook перед каждым коммитом — успешное прохождение полного набора тестов через CTest после сборки актуального кода.
- Сборка должна быть настроена с `BUILD_TESTS=ON`. Перед каждым коммитом выполнить последовательно:

  ```sh
  cmake --build build
  ctest --test-dir build --output-on-failure --no-tests=error
  ```

- Ошибка сборки, отсутствие тестов или любой упавший тест блокируют коммит. После изменения кода повторить проверку; старый успешный запуск не подтверждает новые изменения.
- При изменении поведения проверять классы эквивалентности, границы и существенные ошибки; ограничения типов проверять при компиляции.
- Это обязательное правило рабочего процесса. Наличие этого файла само по себе не устанавливает автоматический Git hook.

## Ветки и документация

- Новые этапы выполнять в отдельных ветках от `dev`. Порядок интеграции: feature → dev → main; в main переносить готовую стабильную версию с заменой соответствующего legacy-кода.
- После успешного hook (сборка и полный CTest) можно самостоятельно создавать коммиты через `commit-specialist` без отдельного подтверждения пользователя. Разделять изменения на небольшие смысловые коммиты и проверять staged diff перед каждым коммитом.
- Проверенную feature можно интегрировать напрямую в `dev` и публиковать `dev` без обязательного PR и повторного подтверждения. Перенос `dev` в `main` выполнять по отдельному запросу пользователя.
- В `architecture-plan.md` записывать решения, изменения, результаты проверок и ограничения; в `todo.md` обновлять статус задачи.
- `architecture-plan.md` оставлять локальным и не включать в коммиты согласно указанию пользователя.
- Контракты команд сверять с официальной документацией Valkey: синтаксис, возвращаемые значения и ошибки. Расхождения фиксировать явно.

## Порядок завершения задачи

1. Проверить текущую ветку и рабочее дерево, сохранить чужие и локальные изменения. Создать ветку от актуального `dev` под одну небольшую задачу.
2. Выполнить задачу по её критериям, обновить тесты при изменении поведения и записать результат в локальный журнал.
3. Перед каждым коммитом пройти hook, проверить staged diff и создать смысловой коммит через `commit-specialist`. Журнал в коммит не включать.
4. Интегрировать готовую ветку в `dev`: предпочитать fast-forward, когда это возможно; при merge-коммите сначала подготовить слияние без коммита, затем собрать и проверить итоговое дерево через CTest.
5. Перед push проверить итоговый `dev`. Публиковать обычным push без переписывания удалённой истории. Не переносить незавершённые задачи в `main`.
6. После push проверить GitHub Actions для опубликованного SHA. CI запускается на Ubuntu, macOS и Windows; локальный успех и запуск workflow ещё не означают успех всей матрицы. При падении разобрать причину, исправить и повторить проверки.
7. PR необязателен. Для обычной работы достаточно CI на push; PR создавать только по запросу. Запуск по событию `pull_request` проверяется отдельно при наличии PR.
8. В итоговом сообщении указать изменения, проверки, коммиты, опубликованные ветки и статус CI. Если CI ещё выполняется или его статус недоступен, сообщить это явно со ссылкой на запуск, когда она доступна.
